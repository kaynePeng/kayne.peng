调过几个 agent 之后，我发现一件挺反直觉的事：同一个模型、同一套 prompt，换一套工具定义，成功率能从「能用」掉到「别用」。问题几乎都不在模型身上，在工具身上。

## 一、工具不是函数，是给模型看的界面

人靠文档理解接口，模型靠 schema 理解工具。名字、描述、参数说明，是它唯一的说明书。

- 名字用「动词 + 名词」：`search_orders` 比 `query` 好，模型不需要猜你在查什么
- 描述要写清「什么时候该用、什么时候不该用」，而不是复述参数名
- 参数越少越好：五个可选参数的工具，模型基本会漏掉两个

我现在加一个新工具，不先写 prompt，先让模型在二十条真实任务上试一遍：它会不会选、参数填得对不对。选错了就改描述，改完再试——九成的「模型不听话」其实是描述没写清。

## 二、返回值要有形状，不要丢一大段自然语言

工具返回纯文本，模型只能猜。结构化的返回才能让下一步稳定：

```
{ ok: false, code: 'NOT_FOUND', message: '订单号不存在', retryable: false }
```

- `retryable` 决定要不要再试一次，这一位比错误文案重要
- 空结果要显式表达（`ok: true, items: []`），不要用空字符串
- 别把几百行原始日志原样塞回去，噪声会把模型带偏

## 三、粒度：一个工具只做一件说得清的事

最容易踩的坑是大而全的 `execute(action, params)`：模型要在参数里再选一次动作，选错一次全盘皆错。

原子工具多几个没关系，选择成本远低于参数拼装成本。但也不能走到另一个极端——把一次业务动作拆成七八步，模型会在中间丢掉上下文。

判断标准只有一条：这个工具对应的事情，模型能不能用一句话说清。

## 四、写操作要有身份证

读操作出错只是白跑一次，写操作出错就是脏数据。所以写类工具我坚持三条：

- **幂等键**：同一次意图重复调用只生效一次
- **dry run**：先返回「将要做什么」，不落库
- **可回滚的凭据**：版本号，或者变更前后的快照

模型会重试，也会因为上下文抖动把同一个动作发两次。这些防御不是给模型留面子，是给自己留退路。

## 五、失败要分类，不要一律抛异常

- **技术失败**（超时、5xx、限流）：可重试，带退避
- **业务拒绝**（权限不足、参数不合法）：不可重试，要让模型知道该换个做法
- **结果不可用**（查到了但内容为空或过期）：给明确信号，让它换查询而不是重试原句

这三类混成一个 error，模型就只会原地重试。agent 跑飞，多半是从这里开始的。

## 怎么判断工具层变好了

准备二十条真实任务，每条只标「期望调用的工具序列」，不标答案。每次改完工具定义跑一遍，看三件事：

- 选对工具的比例
- 平均步数（通常工具变好，步数会下降）
- 死循环和重复调用的次数

这三项比最终答案写得漂不漂亮，更能说明系统健不健康。

一句话：模型的能力上限由模型决定，能不能兑现由工具决定。
