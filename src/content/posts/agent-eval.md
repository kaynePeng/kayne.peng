给 agent 做评测，最容易犯的错是只看它最后说了什么。答案是整个流程里唯一被看见的产物，但决定它明天还能不能用的，是中间那几步。

## 一、为什么不能只看答案

两个 agent 都答对了：

- A：一次查对，两步结束
- B：试了四个工具、重试五次、绕了一圈才凑对

答案一样。但 B 的成本是三倍、延迟是五倍，下一次遇到稍微不同的输入就会崩。只看答案，这两种系统在报表上长得一模一样。

## 二、轨迹至少记这四样

- 它想干什么（这一步的意图）
- 调了哪个工具、参数是什么
- 返回摘要（错误码、条数、关键字段）
- 这一步花了多久

有了这四样，失败才能被分类；只有一句「效果不好」，什么也改不了。

## 三、三类指标要一起看

- **任务成功率**：可验收的完成条件达成比例
- **效率**：平均步数、重复调用率、弯路率（走了不该走的分支）
- **成本**：单任务的 token 与工具调用次数

只看成功率，会奖励「暴力穷举」；只看成本，会惩罚必要的核对。三个一起看，才知道改动是让系统变好了，还是只是变便宜了。

## 四、失败归到五类

- **选错工具**：描述没写清
- **参数错**：schema 太宽，或者没有示例
- **早停**：完成条件没定义
- **死循环**：错误没分类，模型不知道要换策略
- **幻觉结果**：工具返回太模糊，模型自己补了细节

前两类改工具层，后三类改流程和校验。混成一句「效果不好」，就只能靠反复调 prompt 碰运气。

## 五、问题集从真实日志里捞

自己编的题目总是太干净，模型一上手就过。我现在从线上轨迹里挑题：出过错的、用户重问过的、步数超过十步的。二十到三十条就够用，让五类失败各占几条。

改一次跑一次，看的是同一批题目的通过率变化，而不是新题目的观感。

一句话：agent 的评测对象不是答案，是它怎么走到答案的。
