聊天机器人答错，用户笑一下就过去了；agent 改错，用户的数据没了。差别不在智能程度，在副作用。

## 一、先把动作分级，别一上来就全自动

我会把 agent 能做的事分成四档，每一档的批准方式完全不同：

- **只读**：查数据、读文档、算指标——不需要批准，随便跑
- **建议**：起草文案、出方案、生成待办——用户点一下采纳
- **代执行**：发消息、改配置、下单——每次执行前确认
- **全自动**：定时巡检、自动补数据——必须先有预算上限和回滚能力才开

大多数关于「agent 很危险」的争论，其实是把第四档的能力，装进了第一档的壳子里。

## 二、确认点放在不可逆动作之前

不是每一步都弹窗，那等于没做 agent。我的做法是：读和算随便跑，只有「写」之前停下来。

确认框要给出三样东西，否则用户只能盲点：

- 将要做什么（自然语言，加上具体参数）
- 影响范围（几条记录、哪个环境）
- 能不能撤销

## 三、留痕：事后要能回答「它为什么这么做」

每次运行存一条轨迹：输入、每一步的工具与参数、返回摘要、耗时、最终动作。出问题时这是唯一能复盘的东西，比翻日志快得多。

轨迹还要写成人能读懂的样子——不是给机器看的 JSON 堆，而是「第 3 步查了订单，第 4 步决定退款」这种叙述。否则复盘的时候，你面对的还是黑箱。

## 四、三顶帽子：步数、预算、时间

agent 失控的表现通常是三个「一直」：一直试、一直花、一直转。

- **步数上限**：超了就停，把半成品和停下的原因交回去
- **成本上限**：单次任务给一个 token 预算
- **时间上限**：超时打断，别让用户等一个没有尽头的加载态

上限不是限制能力，是让失败变成可控的失败。

## 五、终止条件不能由模型说了算

模型说「完成了」不算完成。要有外部校验：

- 目标状态是否真的达成
- 写操作是否真的落库
- 返回是否符合约定的字段

我现在给每个任务定义一个可验证的完成条件，模型只是执行者，验收由代码做。这一步不做，前面四条都会被「看起来做完了」绕过。

一句话：agent 的价值在「能动手」，风险也在「能动手」。能力上线之前，先把刹车装好。
